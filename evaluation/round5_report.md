## 6. 문제 항목과 원인 (고칠지는 사용자 결정)

⑥ 직접 확인에서는 실패한 항목이 없습니다. ③–⑤에서 나온 문제와 확인한 원인입니다.

1. **⑨가 표현에 따라 걸리지 않음 (재리뷰 day07 113행).** 설명이 "`status` 변수가 **초기화되지 않은** 상태"라서 ⑨의 주장 패턴(NameError·UnboundLocalError·"정의되지 않"·"미정의" 등)에 걸리지 않았습니다. 코드는 `try/except/else`의 모든 경로에서 `status`를 정의하므로(4절 실험에서 확인) 패턴만 넓히면 제거됩니다.
2. **context_precision 0.711 → 0.453 (RAGAS).** 원인 두 가지를 실행 기록(`output.json`의 contexts 순서, `trace.json`의 `search_evidence` 호출)으로 확인했습니다.
   - **(a) 줄 길이 근거 청크가 맨 뒤에 붙음 — 4·15·17번:** round3 이후 줄 길이 지적은 출력 검증이 ruff로 만들고, 리뷰어는 `PEP8-maximum-line-length`를 검색하지 않습니다. 그 청크는 출력 검증이 contexts 끝에 덧붙이므로(`src/review/graph.py`의 `retrieved.setdefault`) 정답 근거가 항상 마지막 순위가 됩니다(15번 6/6, 4번 6/6, 17번 9/9). 2차에서는 리뷰어가 직접 검색해 1순위였습니다.
   - **(b) 버그 리뷰어의 넓은 첫 검색 — 4·6·15·17번:** Sonnet 버그 리뷰어가 diff에 구버전 API가 없어도 "LangChain deprecated API LLMChain …" 같은 넓은 검색을 먼저 해, `DEP-*` 청크 5개가 정답 PEP 8 청크 앞에 놓입니다(예: 6번 `PEP8-imports` 9/9).

   - **결정 (사용자, 2026-11-13): 근거 목록 순서는 바꾸지 않습니다.** 대신 검색 결과로 계산한 값과 정답 청크 순위를 함께 보고합니다(4절 표). (b)는 버그 리뷰어 검색 규칙으로 다음 개선 후보에 올렸습니다.
