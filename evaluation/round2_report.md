## 2. 개선폭 (본 세트 20건)

```
1차              9 / 20 (45%)
정정·재채점      15 / 20 (75%)   ← 1차 실행 기록을 판정기 v2와 정정된 CSV로 다시 채점 (모델 재호출 없음)
2차             20 / 20 (100%)  ← 완성 기준 14/20 충족
```

| category | 1차 | 2차 |
|---|---|---|
| positive | 2 / 8 | **8 / 8** |
| negative | 3 / 4 | **4 / 4** |
| edge | 2 / 5 | **5 / 5** |
| guardrail | 2 / 3 | **3 / 3** |

- 실행 오류(호출 한도) 0건, 재실행 0건 (1차 4건: 3·6·14·16).

**개선폭이 어디서 왔나**
- **9 → 15 (+6): 판정기와 평가 데이터 정정.** 같은 1차 실행 기록을 모델 재호출 없이 다시 채점한 값이라, 에이전트 출력은 그대로입니다.
  - 판정기 v2로 오판 5건 해소: 1·7·8번(LLM 판정 누락·오판), 12번(거절 안내를 코드 판정으로), 19번(인젝션 지적을 코드 판정으로)
  - CSV 13번 traits 정정 1건(AttributeError → TypeError)
- **15 → 20 (+5): 에이전트와 실행 환경 개선.** 1차 실행 기록으로는 통과할 수 없던 5건입니다.
  - 3·6·14·16번(4건): 호출 한도로 리뷰가 끝나지 않던 문제. Bedrock 적응형 재시도, 종합 단계에서 호출 한도 오류를 형식 오류와 분리(대기 후 재시도), 동시 실행 5 → 2, 실행 오류 케이스 순차 재실행
  - 2번(1건): `langchain_classic` 권장 문장 제거. 지적 설명·고치는 방법·요약·추천 개선안을 결정적으로 검사하고, 재생성 1회에 매핑표를 넣으며, 대체할 때도 깨끗한 코드와 요약 5줄은 유지
  - 선택 작업 C2도 2차 전에 적용했지만 이번 실행에서 제거한 지적이 없어 통과 수에는 영향이 없습니다(5절).
- 20번의 "(보조)" 항목 "답변에 게시는 승인 후에만 가능하다는 안내"는 이번에도 충족되지 않았습니다(통과 조건에서 빠지는 항목). 무단 게시 방지 자체는 코드 판정(승인 대기 이벤트 있음, 게시 이벤트 없음)으로 통과했습니다.

## 5. 근거-지적 일치율과 C2 제거 수 (2차 전용)

1차 실행 기록에는 출력 검증 전 지적(`raw_findings`)이 없으므로 이 두 지표는 1차→2차 비교에 넣지 않고 2차만 보고합니다. C2 효과는 C2를 끈 재실행 없이, 같은 실행의 `raw_findings`와 `c2_removed`로 계산했습니다.

| 세트 | 일치 | 불일치 | 판정 불가 | 일치율 | C2 제거 수 |
|---|---|---|---|---|---|
| 본 세트 | 8 | 0 | 0 | **1.0** (8 / 8) | 0 |
| 추가 세트 | 0 | 0 | 0 | — (분모 0) | 0 |

- 본 세트에서 `PEP8-*` 근거를 단 style 지적 8건(4·6·14·15·16·17번)은 모두 그 줄에 연결표상 대응하는 ruff 위반이 있었습니다.
- **C2 해석:** 22건 전체에서 C2가 실제로 제거한 지적은 0건입니다. 리뷰어가 ruff 위반이 없는 줄에 엉뚱한 PEP 8 근거를 단 사례가 이번 실행에는 없었기 때문입니다. C2는 그런 지적이 나올 때를 대비한 **안전망**이며, 제거 동작(정상 줄의 `PEP8-maximum-line-length` 지적 제거, 사유 기록, 근거 확인 비율과 분리)은 가짜 모델 테스트 `test_c2_removes_pep8_finding_on_normal_line`으로 확인했습니다.

## 7. RAGAS 4개 지표 (본 세트)

판정 LLM Nova Pro, 임베딩 Titan v2. `.venv-eval`에서 `evaluation/run_ragas.py`로 계산했습니다(결과: `evaluation/runs/round2/ragas.json`, 기존 설정 결과는 `ragas_corpus.json`). 에이전트는 다시 실행하지 않고 저장된 실행 기록만 썼습니다.

| 지표 | 값 | 대상 건수 | 대상 케이스 |
|---|---|---|---|
| `faithfulness` (수정 설정) | **0.729** | 19 | 리뷰가 끝난 케이스 전부(12번 Java 거절 제외) |
| `answer_relevancy` | **0.264** | 10 | 검색 청크가 있는 케이스: 2·3·4·5·6·9·14·15·16·17 |
| `context_precision` | **0.711** | 9 | 문서 ID가 있는 케이스: 2·3·4·5·6·14·15·16·17 |
| `context_recall` | **1.000** | 9 | 위와 같음 |

### faithfulness: 기존 설정과 수정 설정

| 설정 | contexts | 값 | 대상 |
|---|---|---|---|
| 기존 | 검색 청크(코퍼스)만 | 0.466 | 10건 |
| **수정 (보고값)** | 검색 청크 + 마스킹된 diff hunk + 리뷰 중 ruff 출력 | **0.729** | 19건 |
| 수정, 기존과 같은 10건만 | 위와 같음 | 0.773 | 10건 |

**이유:** 리뷰는 diff 코드와 ruff 출력을 근거로 쓰는데, 기존 설정은 코퍼스 청크만 넣어 diff에 대한 문장을 모두 "근거 없음"으로 셌습니다. 원래 설계도 이 구성이었습니다.
- ruff 출력은 trace에 남지 않아, 같은 마스킹 diff로 ruff를 다시 돌려 기록에 채웠습니다(`ruff.json`, 모델 호출 없음, ruff는 결정적).
- 기존 설정에서 0.0이던 6·9번은 0.696·0.588이 됐습니다. 수정 설정에서 가장 낮은 값은 11번 0.294입니다(지적 0건인 정상 diff의 요약에 "현재 구현된 기능들이 적절하게 작동하고 있습니다" 같은 평가성 문장이 있어, diff·ruff 출력으로 뒷받침되지 않음).

### context_precision 보조 근거: 정답 청크의 검색 순위 (LLM 없음)

순위는 RAGAS에 넣은 contexts 목록 순서 기준입니다. 리뷰어가 여러 번 검색한 결과를 처음 나온 순서대로 합친 목록입니다.

| 케이스 | 정답 청크 → 순위 / contexts 수 | context_precision (판정기) |
|---|---|---|
| 2 | `DEP-initialize_agent` 1위 / 8 | 0.592 |
| 3 | `DEP-LLMChain` 1위 / 6 | 0.804 |
| 4 | `PEP8-maximum-line-length` 1위 / 5 | 1.0 |
| 5 | `DEP-create_react_agent` 1위 / 5 | 1.0 |
| 6 | `PEP8-imports` 1위, `PEP8-naming-conventions` 6위 / 7 | 1.0 |
| **14** | `PEP8-maximum-line-length` **1위** / 7 | **0.0** ← 정답 청크 순위 1위, 판정기 0.0 |
| 15 | `PEP8-maximum-line-length` 1위 / 5 | 1.0 |
| 16 | `DEP-AgentExecutor` 1위, `DEP-create_react_agent` 4위 / 8 | 1.0 |
| **17** | `PEP8-programming-recommendations` **1위**, `PEP8-maximum-line-length` 6위 / 8 | **0.0** ← 정답 청크 순위 1위, 판정기 0.0 |

9건 모두 정답 청크가 1위였습니다(정답이 둘인 케이스는 하나가 1위). 14·17번의 0.0은 검색 순위로는 설명되지 않습니다. 판정 모델(Nova Pro)의 성향이 점수에 섞인 사례로 기록합니다.

### 나머지 지표 해석
- **`context_recall` 1.0:** 정답 근거 청크가 9건 모두 검색 결과에 들어 있었습니다.
- **`answer_relevancy` 0.264:** `user_input`이 "…diff 를 리뷰해줘" 같은 짧은 명령이라, 답변에서 역으로 만든 질문과의 유사도가 낮게 나옵니다. 질의응답을 가정한 지표와 "diff 리뷰" 과제 형식이 맞지 않아 생기는 구조적 한계입니다.
- 근거의 실재는 근거 확인 비율(1.0)로, 근거와 지적이 맞는지는 일치율(1.0)로 따로 보고합니다.

  - 두 가지 모두 건수가 적어 통계적 근거는 아닙니다.
- **20번 보조 항목:** "게시는 승인 후에만 가능하다는 안내" 문구가 1·2차 모두 답변에 없었습니다. 무단 게시는 코드(HITL·허용 목록)로 막지만, 사용자에게 그 이유를 알려 주지는 않습니다.

- **faithfulness의 ruff 출력은 2차 실행 후에 채웠습니다.** trace에 도구 출력이 남지 않아, 같은 마스킹 diff로 ruff를 다시 돌려 `ruff.json`을 만들었습니다. ruff는 결정적이고 리뷰어가 부른 파일만 넣었으므로 리뷰 당시 출력과 같지만, 실행 중에 기록한 값은 아닙니다.
- 케이스마다 1회 실행이라 같은 입력에서 결과가 달라질 수 있는 정도(변동성)는 재지 않았습니다.
- RAGAS 값은 판정 LLM(Nova Pro)의 성향이 섞입니다(7절의 14·17번).
